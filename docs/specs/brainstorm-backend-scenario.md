# 브레인스토밍 제품·백엔드 정책 시나리오

> 문서 성격: 내부 제품·백엔드 설계 기록(소장용)
>
> 최종 갱신: 2026-09-06
>
> 우선순위: `docs/requirements/CURRENT_REQUIREMENTS.md`가 이 문서보다 우선한다.

이 문서는 브레인스토밍 캔버스, 보드 버전, PRD 반영, 협업 충돌 및 기여도 계산에 관한 제품
시나리오와 서버 계약을 정리한다. 초기 UI 목업과 첨부 자료는 요구사항을 추출하기 위한 참고
자료였으며, 현재 구현 여부는 각 절의 명시적인 상태와 최우선 정책 문서를 기준으로 판단한다.

## 1. 현재 제품 범위

현재 사용자 화면과 서버 계약은 다음 기능을 제공한다.

- PRD 유형에 따라 달라지는 섹션별 칸
- 캔버스 상단 미분류 아이디어 영역
- 메모를 섹션 칸으로 드래그해 분류
- 섹션별 아이디어 개수와 채택 개수
- 섹션별 `AI PRD 적용` 미리보기
- 전체 `PRD에 반영` 진입
- AI 호출 없이 섹션별 아이디어 현황을 보여주는 `분류 결과`
- 확대, 축소, 화면 이동, 화면 위치 초기화
- 같은 섹션 연결선과 다른 섹션 연결선의 시각적 구분
- 전체 / 채택됨 / 기본 상태 필터
- 미분류·전체·채택 메모 실시간 개수
- 보류 메모 전용 하단 영역과 복원
- PRD 전체 또는 질문별 코멘트
- 튜터·관리자 코멘트 권한
- 관리자에게만 공개되는 AI 기반 코멘트 반영 기여도 평가

다음 기능은 현재 일반 사용자 화면에서 제공하지 않는다.

- AI 브레인스토밍 분석
- AI 항목 자동 분류와 추천 적용
- 사용자용 기여도 결과와 근거 화면
- 사용자의 삭제 메모 복원 화면

다음 항목은 제품 범위에서 제외했거나 별도 결정이 필요하다.

- 제목 카드 생성 UI
- 브레인스토밍 Markdown 복사와 파일 다운로드: 제거됨
- 실행 취소와 다시 실행 UI
- 실시간 접속자와 마우스 표시

## 2. 캔버스와 PRD 관계

PRD 하나에는 순번이 있는 브레인스토밍 캔버스를 여러 개 둘 수 있다. 최초 캔버스는 `ver.1`이며 새 버전은 사용자가 현재 보고 있는 캔버스를 복제해 만든다.

```text
unique (canvas.prd_id, canvas.version_number)
```

사용자가 처음 브레인스토밍 화면에 들어왔을 때 캔버스가 없으면 권한을 확인한 뒤 `ver.1`을 한 번만 생성한다. 동시에 여러 요청이 들어와도 같은 버전이 중복 생성되지 않도록 `(prd_id, version_number)` 유니크 제약과 idempotency key를 사용한다.

화면에 처음 진입하면 `display_order`가 가장 앞선 최신 캔버스를 연다. 왼쪽 버전 목록의 순서는 편집 권한자가 바꿀 수 있고, 가장 위 보드를 최신으로 지정한다. 최신 보드 하나만 메모·연결선·PRD 반영을 편집할 수 있으며 이전 버전은 조회 전용이다. 최신 보드를 삭제하면 다음 순서의 보드를 즉시 최신으로 승격한다. 이력을 보호하기 위해 마지막 남은 보드는 삭제할 수 없고, 삭제된 보드는 소프트 삭제한다. 메모·연결선·viewport·polling cursor는 선택한 캔버스별로 분리한다.

새 버전은 소프트 삭제되지 않은 메모와 활성 연결선을 복제한다. 복제된 메모는 새 UUID와
`version=1`을 받지만 원본 계보를 나타내는 `lineage_id`를 유지한다. 따라서 여러 캔버스에 복제된
같은 아이디어는 기여도에서 한 번만 집계한다. 최초 작성자와 의미 있는 내용 편집자를 계보 전체에서
추적하고 실제 PRD 반영 confidence를 적용하며, 담당자·좌표·섹션 변경만으로 새 기여가 생기지
않는다. 새 보드에서 새로 작성한 메모는 새로운 `lineage_id`를 가진다.

PRD가 삭제되거나 사용자의 접근 권한이 사라지면 캔버스도 조회할 수 없다. 캔버스를 직접 조회할 수 있다는 이유로 PRD 권한 검사를 생략하지 않는다.

## 3. PRD 유형별 섹션 칸

캔버스의 섹션 칸은 프론트에 고정된 배열이 아니라 해당 PRD의 실제 섹션을 기준으로 만든다.

- 신규 프로젝트 PRD: 신규 프로젝트 템플릿의 섹션
- 신규 기능 PRD: 신규 기능 템플릿의 섹션
- 기능 개선 PRD: 기능 개선 템플릿의 섹션

각 칸은 `section_id`, 표시 순서, 제목을 가진다. 노드는 `section_id`로 칸에 속한다.

- 미분류 아이디어: `section_id = null`
- 섹션에 분류된 아이디어: `section_id = 해당 PRDSection.id`

PRD 유형을 변경해 템플릿 섹션이 달라지는 기능은 현재 범위에서 허용하지 않는다. 향후 허용한다면 기존 노드의 섹션 매핑을 먼저 처리해야 한다.

## 4. 노드 종류

메모와 제목 카드는 같은 노드 테이블에 저장하되 `node_type`으로 구분한다.

- 일반 메모: `node_type = note`
- 제목 카드: `node_type = title`

일반 메모는 다음 값을 가진다.

- 내용
- 색상
- 좌표
- 섹션
- 작성자
- 담당자
- 상태
- 버전

노드와 연결선의 ID는 DB 기본값으로 UUID를 생성한다. 프론트의 현재 시각이나 배열 순번을 영구 ID로 사용하지 않는다.

제목 카드는 내용, 색상, 좌표, 섹션, 버전만 가진다. 작성자, 담당자, 채택·보류 상태는 적용하지 않는다. 제목 카드에도 연결선을 만들 수 있다.

현재 UI에는 제목 카드 생성 동작이 없으므로, API와 화면을 함께 추가하기 전까지 일반 사용자가 제목 카드를 생성하는 기능은 노출하지 않는다.

## 5. 일반 메모 상태

일반 메모 상태는 `status` 하나만 사용한다.

- `default`: 기본
- `accepted`: 채택됨
- `held`: 보류

`is_accepted`, `is_held`, `pending` 같은 중복 상태 필드는 만들지 않는다.

제목 카드는 상태를 가지지 않는다. 서버는 제목 카드에 대한 상태 변경 요청을 거절한다.

## 6. 메모 생성

메모를 만들 때 로그인 사용자가 작성자가 된다. 프론트가 임의의 `author_id`를 선택해 보내지 않는다.

최초 담당자도 작성자와 동일하게 지정한다.

```text
author_id = authenticated_user.id
assignee_id = authenticated_user.id
```

요청 예시:

```json
{
  "content": "사용자 문제를 먼저 검증한다",
  "color": "yellow",
  "x": 540,
  "y": 120,
  "section_id": null,
  "idempotency_key": "uuid"
}
```

서버는 다음을 검증한다.

- 로그인과 PRD 편집 권한
- 내용이 공백이 아닌지
- 최대 글자 수
- 허용된 색상인지
- 좌표가 유효한 숫자인지
- `section_id`가 같은 PRD에 속하는지

작성자는 생성 후 바꿀 수 없다. 담당자는 별도 권한이 있는 사용자가 다른 PRD 참여자로 변경할 수 있다.

## 7. 메모 수정과 담당자

메모 내용은 작성자 또는 PRD 편집 권한이 있는 사용자가 수정할 수 있다. 작성자 표시용 `author_id`는 수정하지 않는다.

담당자는 해당 PRD의 현재 참여자만 지정할 수 있다.

- 담당자 없음: `assignee_id = null`
- 담당자 지정: `assignee_id = PRD 참여자 user_id`

팀원이 PRD에서 빠졌는데 그 팀원이 담당자인 메모가 있다면 담당자를 해당 메모의 작성자로 되돌린다.

```text
if removed_user_id = assignee_id:
    assignee_id = author_id
```

작성자도 더 이상 PRD 참여자가 아니라면 과거 작성자 기록은 유지한다. 이 경우 담당자를 작성자로 되돌리는 것은 허용하되, 해당 사용자가 다시 편집 권한을 얻는 것은 아니다. 관리자가 활성 참여자에게 담당자를 재배정할 수 있다.

## 8. 미분류 영역과 드래그 분류

새 메모는 기본적으로 미분류 영역에 생성한다.

사용자가 메모를 섹션 칸 안으로 드래그하고 마우스를 놓으면 최종 좌표와 `section_id`를 한 요청으로 저장한다.

```http
PATCH /api/brainstorm/nodes/{node_id}/position
```

```json
{
  "x": 680,
  "y": 510,
  "section_id": 42,
  "version": 7
}
```

드래그 중간 좌표는 서버에 계속 보내지 않는다. 마우스를 놓았을 때만 저장한다.

브레인스토밍 API는 다음 이동을 모두 허용한다.

- 미분류 -> 섹션
- 섹션 A -> 섹션 B
- 섹션 -> 미분류
- 같은 섹션 안에서 위치만 변경

서버는 화면 픽셀로 섹션을 추측하지 않고, 프론트가 보낸 `section_id`가 유효한지 검증한다.

## 9. 화면 확대, 이동, 초기화

확대 비율과 화면 위치는 사용자와 캔버스 조합으로 저장한다.

- `viewport_x`
- `viewport_y`
- `zoom_level`
- `updated_at`

허용 확대 범위는 프론트와 서버 모두 30%부터 200%로 고정한다.

화면 초기화는 저장된 값을 기본값으로 되돌린다. 다른 팀원의 화면 위치에는 영향을 주지 않는다.

화면 이동 중 매 프레임 저장하지 않고, 이동이나 확대가 끝난 뒤 debounce해 저장한다.

## 10. 상단 개수와 필터

상단에는 다음 개수를 표시한다.

- 전체 메모: 삭제되지 않고 보류가 아닌 일반 메모
- 미분류: 전체 메모 중 `section_id = null`
- 채택: 전체 메모 중 `status = accepted`
- 보류: 삭제되지 않고 `status = held`인 일반 메모

제목 카드는 메모 개수에 포함하지 않는다.

캔버스 필터는 다음을 지원한다.

- 전체
- 채택됨
- 기본

보류 메모는 필터 결과가 아니라 하단 보류 영역에 표시한다. 필터 때문에 노드가 숨겨지면, 숨겨진 노드와 연결된 연결선도 화면에서만 숨긴다. 데이터는 삭제하지 않는다.

## 11. 보류는 삭제가 아니다

보류는 메모를 제거하는 동작이 아니라 `status = held` 태그를 지정하는 동작이다.

보류할 때 다음 값은 보존한다.

- 메모 내용
- 작성자
- 담당자
- 색상
- 변경 기록

보류 시 현재 섹션 연결을 해제해 `section_id = null`로 만들고, 메모에 연결된 연결선은 영구 삭제한다. 연결선 행은 복원하지 않으며 감사 로그에 연결된 두 노드 ID와 `reason = node_held`를 기록한다.

연결선은 의미 관계를 나타내므로, 보류 중 상대 메모나 보류 메모의 내용이 바뀌었다면 예전 연결이 여전히 유효하다고 자동 판단할 수 없다. 따라서 복원할 때 과거 연결선을 되살리지 않는다. 사용자가 내용을 확인한 뒤 필요하면 다시 연결한다.

보류 해제 시 보류 직전 섹션이 아직 유효하면 그 섹션과 좌표 맥락으로 돌아간다. 직전 섹션이
없거나 삭제됐다면 미분류 영역의 안전한 기본 좌표로 돌아간다.

```text
status = accepted 또는 default
section_id = held_from_section_id 또는 null
connections = none
```

미분류 복원 좌표는 서버가 안전한 기본 위치를 계산해 반환한다. 여러 메모를 동시에 미분류로
복원할 때는 겹치지 않게 배치한다.

## 12. 삭제와 복원

메모와 제목 카드는 소프트 삭제한다.

- 삭제: `is_deleted = true`, `deleted_at` 기록
- 복원: `is_deleted = false`, `deleted_at = null`

노드가 삭제되면 연결된 연결선도 소프트 삭제한다. 노드를 복원할 때 상대편 노드가 살아 있으면 연결선도 복원한다. 상대편 노드가 삭제 상태면 연결선을 복원하지 않는다.

이 규칙은 사용자가 `삭제`를 실행한 경우에만 적용한다. `보류`는 별도 정책에 따라 연결선을 영구 삭제하므로 메모를 보류에서 복원해도 연결선이 복원되지 않는다.

삭제 데이터는 30일 동안 복원할 수 있고 이후 백그라운드 작업으로 영구 삭제한다.

프론트는 삭제 성공 후 노드를 화면에서 제거하지만 서버 데이터는 복구 기간 동안 소프트 삭제
상태로 유지한다.

## 13. 연결선

일반 메모와 제목 카드 사이에 연결선을 만들고 삭제할 수 있다.

서버는 다음 연결을 거절한다.

- 자기 자신과의 연결
- 같은 두 노드 사이의 중복 연결
- 다른 PRD 캔버스의 노드와 연결
- 삭제된 노드와 연결
- 권한 없는 사용자의 연결 변경

같은 섹션 내부 연결과 다른 섹션 간 연결은 데이터 모델상 같은 연결이다. 실선·점선과 색상 구분은 화면 표현일 뿐 별도 의미로 저장하지 않는다.

연결선의 방향과 관계 종류는 결정 전까지 저장하지 않는다.

연결선 ID는 DB가 UUID 기본값으로 생성한다. 생성 요청에는 별도의 idempotency key를 보내 네트워크 재시도로 같은 연결선이 두 번 만들어지지 않게 한다.

## 14. 자동 정렬

자동 정렬은 다음 노드를 대상으로 한다.

- 삭제되지 않은 일반 메모
- 보류 상태가 아닌 메모

제목 카드와 보류 메모는 자동 정렬에서 제외한다.

섹션에 속한 메모는 해당 칸 안에서 정렬하고, 미분류 메모는 미분류 영역에서 정렬한다. 모든 새 좌표는 한 번의 일괄 요청으로 저장한다.

```http
PATCH /api/brainstorm/nodes/batch-position
```

자동 정렬 결과가 섹션 높이를 넘는다면 좌표를 겹쳐 저장하지 않는다. 섹션 영역 확장, 스크롤 또는 정렬 중단 중 하나를 정책으로 선택하고 사용자에게 결과를 안내한다.

자동 정렬 전체를 하나의 변경 작업으로 기록해 한 번에 실행 취소할 수 있게 한다.

## 15. 분류 결과와 Legacy AI 항목 분류

현재 사용자 화면의 `분류 결과`는 AI 추천 기능이 아니다. 서버가 노드의 저장된 `section_id`와
`status`를 기준으로 전체·미분류·채택·보류 및 섹션별 개수를 계산한다. 좌표만 보고 섹션을
추측하지 않으며 사용자가 메모를 이동하면 최종 위치 저장 응답과 polling 이벤트로 다시 집계한다.

아래 AI 추천 흐름은 과거 구현의 호환성 기록이다. 현재 사용자 화면에서는 제공하지 않고 신규
기능도 이 계약에 의존하지 않는다. 통합 저장소에서 기존 호출자가 없음을 확인한 뒤 Legacy API와
프롬프트 제거 여부를 별도 결정한다.

1. 사용자가 AI 항목 분류를 요청한다.
2. 서버는 미분류 일반 메모와 현재 PRD 섹션 목록만 AI에 전달한다.
3. AI는 메모별 추천 `section_id`와 이유를 반환한다.
4. 화면에서 추천 결과를 미리 보여준다.
5. 사용자가 선택한 추천만 일괄 반영한다.

AI가 좌표나 섹션을 즉시 바꾸지 않는다. 사용자의 확인 전에는 원본 데이터가 변하지 않는다.

제목 카드, 보류 메모, 삭제 메모는 AI 분류 대상에서 제외한다.

## 16. Legacy AI 브레인스토밍 분석

이 절은 과거 AI 분석 API의 호환성 기록이다. 현재 사용자 화면에서는 제공하지 않으며, 화면의
분류 결과는 15절의 서버 집계를 사용한다. Legacy API가 호출될 경우에도 정확한 통계는 서버가
계산하고 AI는 그 통계와 실제 메모 내용을 바탕으로 코멘트만 작성한다.

정확한 집계 항목:

- 전체 활성 메모 수
- 채택 메모 수
- 보류 메모 수
- 미분류 메모 수
- 섹션별 전체·채택 메모 수
- 비어 있는 섹션 목록

개수는 AI가 세지 않는다. 서버 집계값을 그대로 사용한다.

AI 코멘트에는 분석에 사용한 노드 ID와 섹션 ID를 기록한다. 사용자가 요청을 취소하면 서버 AI 작업도 취소한다.

분석 결과는 PRD나 메모를 자동 변경하지 않는다.

고정 타이머나 샘플 문장을 실제 분석 결과로 표시하지 않는다.

AI가 실제로 분석할 수 있도록 백엔드는 다음 계약을 구현한다.

```text
feature_type = BRAINSTORM_ANALYSIS
input = PRD 기본 정보 + 섹션 목록 + 활성 메모 내용/상태/담당자 + 연결 정보 + 서버 집계
output = summary + section_findings[] + missing_topics[] + source_node_ids[]
```

AI 출력은 JSON Schema로 검증한다. AI가 반환한 개수는 화면에 사용하지 않고 서버 집계값을 사용한다.

## 17. 섹션별 AI PRD 적용 미리보기

각 섹션의 `AI PRD 적용`은 해당 섹션 아이디어를 PRD에 반영하기 전에 미리보는 기능이다.

미리보기에는 다음을 구분해 보여준다.

- 채택된 아이디어
- 검토 대기 아이디어
- 제외되는 보류·삭제 아이디어

기본적으로 PRD 반영에는 `accepted` 메모만 사용한다. 기본 상태 메모를 포함하려면 사용자가 명시적으로 선택해야 한다.

AI는 해당 섹션의 의미와 메모 내용을 이해할 수 있도록 다음 자료를 함께 받는다.

- PRD 제목, 설명, 유형
- 대상 섹션 제목과 작성 가이드
- 대상 섹션의 질문 ID, 질문 문구, 현재 답변
- 해당 섹션의 채택 메모 내용
- 사용자가 추가로 선택한 기본 상태 메모
- 선택된 메모 사이의 연결 정보

AI는 기존 답변을 보존하면서 메모의 핵심 내용을 자연스럽게 통합한 질문별 답변 초안을 만든다. 메모를 단순히 뒤에 이어 붙이거나 기존 답변을 그대로 덮어쓰지 않는다.

```text
merge_strategy = ai_integrate
```

AI는 기존 답변에서 유지한 내용, 메모에서 새로 반영한 내용, 충돌하거나 반영하지 못한 내용을 구분한다. 결과는 구조화된 형식으로 반환한다.

```json
{
  "section_id": 42,
  "answers": [
    {
      "question_id": 501,
      "draft": "사용자가 해결하려는 핵심 문제는 ...",
      "source_node_ids": ["uuid-1", "uuid-2"],
      "preserved_existing_points": ["기존 답변에서 유지한 핵심 내용"],
      "added_points": ["메모에서 새로 통합한 내용"],
      "confidence": 0.86
    }
  ],
  "unused_node_ids": ["uuid-3"],
  "warnings": []
}
```

`question_id`와 `source_node_ids`는 서버가 다시 검증한다. 미리보기 결과만으로 PRD를 변경하지
않고 사용자의 질문별 승인 요청에서 저장한다.

사용자가 미리보기를 확인하고 `PRD에 반영하기`를 눌렀을 때만 저장한다.

## 18. 전체 PRD 반영

상단 `PRD에 반영`은 모든 섹션의 채택 메모를 한 번에 검토하는 흐름으로 연결한다. 단순히 PRD 상세 화면으로 이동하는 것만으로 반영 완료로 처리하지 않는다.

반영 전 서버는 다음을 다시 확인한다.

- PRD 편집 권한
- 대상 섹션이 아직 존재하는지
- 메모가 삭제·보류 상태로 바뀌지 않았는지
- 미리보기 이후 메모 버전이 바뀌지 않았는지
- 같은 요청이 이미 처리되지 않았는지

미분류 채택 메모가 있으면 자동으로 임의 섹션에 넣지 않는다. 사용자가 섹션을 지정하거나 이번 반영에서 제외한다.

MVP 반영은 일회성 저장이다.

- PRD에서 수정해도 캔버스 원본은 바뀌지 않는다.
- 캔버스에서 수정해도 이미 반영된 PRD 내용은 바뀌지 않는다.
- 다시 반영하려면 사용자가 다시 요청한다.

반영 기록에는 사용한 노드 ID, 노드 버전, 대상 질문 ID, 생성된 문장, 실행 사용자, 실행 시각을 저장한다.

기존 답변이 있는 질문은 AI가 기존 답변과 선택된 메모를 하나의 자연스러운 답변으로 통합한다. 기존 답변, AI 통합 결과, 추가·제외된 내용과 근거 메모를 함께 보여주고 사용자가 질문별로 승인한다.

사용자가 승인하기 전에는 기존 답변을 변경하지 않는다. 승인한 질문만 AI 통합 결과로 저장한다.

## 19. 반영 충돌과 중복 방지

미리보기 후 다른 사용자가 메모나 PRD 질문을 수정할 수 있다.

반영 요청에는 다음 버전을 포함한다.

- 노드별 `version`
- 대상 질문별 `version`
- 미리보기 요청 ID

버전이 다르면 서버는 `409 Conflict`와 변경된 항목을 반환한다. 사용자는 최신 데이터로 미리보기를 다시 만든다.

같은 `idempotency_key`로 반영 요청이 반복되면 PRD 답변을 중복 추가하지 않고 첫 처리 결과를 반환한다.

## 20. Markdown 내보내기

브레인스토밍 Markdown 내보내기는 제품 범위에서 폐기했으며 UI, URL과 백엔드 구현을 제공하지
않는다. PRD 작성 화면의 Markdown 내보내기는 별도 기능으로 유지한다. 이 결정을 되돌리려면 새
제품 결정과 별도 API 계약이 필요하며, 이 문서의 과거 요구사항을 근거로 복원하지 않는다.

## 21. 실시간 협업

같은 PRD 팀원이 접속하면 다음 변경을 실시간으로 반영한다.

- 메모 생성과 수정
- 위치와 섹션 변경
- 상태 변경
- 담당자 변경
- 삭제와 복원
- 연결선 생성과 삭제
- 자동 정렬
- PRD 반영 완료 알림

드래그 중간 좌표는 실시간 이벤트로 계속 저장하지 않는다. 필요한 경우 프레즌스 채널에서 임시 위치만 공유하고, 최종 좌표는 마우스를 놓았을 때 저장한다.

재연결 시 이벤트만 이어받지 말고 서버의 최신 노드, 연결선, 통계를 다시 조회한다.

## 22. 버전 충돌

각 노드와 연결선에 `version`을 둔다.

수정 요청의 버전이 서버와 같을 때만 저장한다. 다르면 `409 Conflict`와 최신 데이터를 반환한다.

내용 수정과 위치 이동이 동시에 발생할 수 있으므로, 가능하면 변경 필드만 PATCH한다. 전체 객체를 덮어쓰면 다른 사용자의 변경을 잃을 수 있다.

## 23. 실행 취소와 변경 기록

다음 작업은 변경 기록으로 남긴다.

- 내용 수정
- 위치·섹션 변경
- 상태 변경
- 담당자 변경
- 삭제·복원
- 연결선 생성·삭제
- 자동 정렬
- AI 분류 일괄 반영
- PRD 반영

자동 정렬과 AI 분류 일괄 반영은 각각 하나의 작업 단위로 실행 취소한다.

감사 로그에는 누가 언제 무엇을 했는지 별도로 남긴다. 작성자 자체는 바꾸지 않는다.

## 24. 코멘트와 튜터 권한

PRD 전체 또는 개별 질문에 코멘트를 달 수 있다.

권한 역할은 다음과 같이 구분한다.

- `owner`: PRD·참여자·권한 관리, 완료, 재개, 편집, 코멘트
- `editor`: 완료 전 PRD·브레인스토밍 편집, AI 요청, PRD 반영, 코멘트
- `tutor`: 조회와 코멘트만 가능하며 완료 후에도 리뷰 코멘트 작성 가능
- `viewer`: 조회만 가능

튜터는 작성 방향을 지도할 수 있지만 메모, 담당자, 연결선, PRD 답변을 직접 변경하지 않는다. 튜터가 남긴 코멘트는 기여도 계산에서 제외한다.

코멘트에는 다음 값을 둔다.

- `prd_id`
- `section_question_id` 또는 `null`
- `author_id`
- `content`
- `author_role_at_created`
- `is_contribution_eligible`
- `created_at`, `updated_at`
- 소프트 삭제 필드

튜터 또는 관리자 지도 목적으로 작성된 코멘트는 생성 시 `is_contribution_eligible = false`로 저장한다. 나중에 사용자 역할이 바뀌어도 과거 코멘트의 기여도 포함 여부가 바뀌지 않게 생성 당시 역할을 보존한다.

팀원인 `owner`가 일반 참여자로 작성한 코멘트는 기여도 계산에 포함한다. `owner`라는 역할만으로 제외하지 않는다.

완료된 PRD에서 일반 팀원은 새 코멘트를 추가하거나 기존 코멘트를 수정할 수 없다. 튜터는 완료 후에도 리뷰 코멘트를 작성할 수 있지만 PRD 내용, 메모, 담당자, 연결선을 변경할 수 없다.

완료 후 작성된 튜터 리뷰 코멘트는 `comment_type = post_completion_review`, `is_contribution_eligible = false`로 저장한다. 해당 리뷰를 반영해 PRD를 수정하려면 관리자가 PRD를 재개해야 한다.

## 25. 팀원 기여도

메모 기여도는 여러 보드 버전에서 아이디어가 발전하는 과정을 보존하면서 실제 PRD 반영 정도를
평가한다.

- 삭제되지 않은 `accepted` 일반 메모만 후보가 된다.
- 실제 `AiPrdApplyItem.source_nodes`에 기록된 메모만 반영 기여로 계산한다.
- 모든 보드 버전에서 같은 `lineage_id`는 하나의 아이디어로 집계한다.
- 최초 작성자와 의미 있는 내용 편집자에게 각각 기여를 인정한다.
- 담당자·위치·섹션·상태만 변경한 행위는 새 내용 기여로 인정하지 않는다.
- 제목 카드, 기본, 보류, 삭제 메모는 점수에서 제외한다.
- 참여자에서 제거된 담당자는 작성자로 되돌리지만, 담당자 변경 자체는 새 기여를 만들지 않는다.

분류 결과의 단순 채택 개수와 최종 기여도 점수를 같은 값으로 사용하지 않는다.

### 메모 기여도

각 lineage가 실제 PRD에 반영된 정도는 반영 기록의 `confidence`로 계산한다. 같은 사용자가 같은
lineage를 여러 버전에서 편집해도 한 번만 인정하며, 같은 lineage에 여러 내용 기여자가 있으면 각
기여자에게 해당 lineage의 반영 confidence를 온전히 부여한다. 기여자끼리 confidence를 나누지
않는다.

```text
user_memo_raw = sum(사용자가 기여한 lineage별 PRD 반영 confidence)
memo_contribution = user_memo_raw / 전체 참여자 memo_raw 합 * 100
```

새 lineage 추적 필드가 생기기 전에 저장된 과거 snapshot은 동일 입력 재평가의 재현성을 위해
당시의 최종 담당자 방식으로 계산한다.

### 코멘트 기여도

AI는 기여도 계산 대상 코멘트가 최종 PRD에 의미적으로 얼마나 반영됐는지 평가한다. 단순히 같은 단어가 있는지만 비교하지 않는다.

AI 입력:

- 완료 시점의 최종 PRD 전문
- 기여도 계산 대상 코멘트
- 코멘트가 달린 질문과 섹션
- 코멘트 작성자 ID

AI 출력:

```json
{
  "comments": [
    {
      "comment_id": "uuid",
      "reflection_score": 80,
      "matched_question_ids": [501],
      "evidence": ["최종 PRD에서 대응되는 요약 문장"],
      "reason": "코멘트의 핵심 제안이 성공 지표에 반영됨",
      "confidence": 0.84
    }
  ]
}
```

각 코멘트의 `reflection_score`는 0부터 100이다. 사용자별 대상 코멘트 점수를 합산한 뒤 전체 사용자 합계가 100이 되도록 정규화한다.

```text
user_comment_raw = sum(eligible comment reflection_score)
comment_contribution = user_comment_raw / sum(all eligible users' raw scores) * 100
```

튜터의 지도·리뷰 코멘트와 `is_contribution_eligible = false`인 코멘트는 AI 입력과 점수 계산에서 제외한다. 팀원인 `owner`의 일반 코멘트는 `is_contribution_eligible = true`로 계산에 포함한다.

### 최종 기여도

```text
total_score = 0.5 * comment_contribution + 0.5 * memo_contribution
```

MVP의 최종 가중치는 코멘트 기여도 50%, 채택 메모 기여도 50%로 확정한다. 팀이나 PRD 유형에 따라 임의로 바꾸지 않는다.

기여도 계산 결과에는 AI 모델·프롬프트 버전, 입력 PRD 버전, 대상 메모·코멘트 ID, 근거, 계산 시각을 함께 저장한다.

PRD를 재개해 내용이 변경된 뒤 다시 완료하면 이전 결과를 덮어쓰지 않고 새 계산 버전을 만든다.

## 26. PRD 완료와 재개

PRD가 `completed` 상태가 되면 일반 사용자의 다음 동작을 잠근다.

- PRD 답변 수정
- 메모 생성·수정·이동·상태 변경
- 담당자와 연결선 변경
- PRD 반영
- 일반 팀원의 코멘트 생성·수정

완료 상태를 다시 `in_progress`로 바꾸는 재개 동작은 `owner` 또는 관리자 권한만 수행할 수 있다. 재개 시 감사 로그에 실행 사용자, 이유, 이전 완료 시각을 기록한다.

튜터의 완료 후 리뷰 코멘트 작성은 잠금 예외다. 리뷰 코멘트는 PRD 내용을 변경하지 않으며 기여도에도 포함하지 않는다.

PRD 완료 트랜잭션 이후 기여도 계산 작업을 시작한다. AI 평가가 실패해도 PRD 완료 자체를 취소하지 않고 `contribution_status = failed`로 기록해 관리자가 재시도할 수 있게 한다.

## 27. 공통 AI 안전장치

Legacy AI 분석·분류, 현재 AI PRD 적용과 코멘트 기여도 평가에는 공통으로 다음을 적용한다.

- 요청 취소 시 서버 작업도 취소
- 사용자·PRD별 짧은 시간 중복 요청 제한
- 사용량과 비용 제한
- 입력 메모 수와 글자 수 제한
- 타임아웃과 이해 가능한 오류 문구
- 참고한 노드와 섹션 기록
- 프롬프트 인젝션 방지를 위한 데이터·지시 분리
- 실패·취소 요청을 사용 성공 횟수에서 제외

AI가 반환한 `section_id`, `node_id`, `question_id`는 신뢰하지 않고 서버 데이터와 다시 대조한다.

AI 기능별 프롬프트는 DB 또는 버전 관리되는 설정으로 구분한다.

- `BRAINSTORM_ANALYSIS`
- `BRAINSTORM_CLASSIFICATION`
- `BRAINSTORM_PRD_APPLY`
- `CONTRIBUTION_EVALUATION`

각 AI 기능은 입력·출력 JSON Schema, 권한, 저장 시점, 실패 처리와 모델 설정을 명시적인 계약으로
관리한다.

## 28. 예외 상황

### 캔버스나 PRD가 없는 경우

PRD가 없으면 `404 Not Found`를 반환한다. PRD는 있지만 캔버스가 없으면 권한 확인 후 한 번만 생성한다.

### 권한이 바뀐 경우

화면을 연 뒤 사용자의 편집 권한이 제거될 수 있다. 이후 저장 요청은 `403 Forbidden`을 반환하고 화면을 읽기 전용으로 전환한다.

### 빈 메모 또는 너무 긴 메모

공백 메모는 생성·저장하지 않는다. 최대 길이를 넘으면 `400 Bad Request`와 허용 길이를 반환한다. 편집 중 내용을 모두 지우면 기존 메모를 자동 삭제하지 않고 저장을 거절한다.

### 잘못된 섹션으로 이동한 경우

다른 PRD의 `section_id`이거나 삭제된 섹션이면 저장하지 않는다. 최신 섹션 목록을 반환하고 미분류로 이동할지 사용자가 선택하게 한다.

### 캔버스 밖으로 이동한 경우

서버는 NaN, 무한대, 과도한 좌표를 거절하거나 허용 범위로 보정한다. 보정했다면 최종 좌표를 응답에 포함한다.

### 한 메모를 두 사용자가 동시에 수정한 경우

먼저 저장된 요청만 성공한다. 늦은 요청에는 `409 Conflict`와 최신 내용, 담당자, 상태, 좌표를 반환한다.

### 드래그 중 다른 사용자가 메모를 삭제한 경우

위치 저장 요청에 `404` 또는 삭제 상태 충돌을 반환한다. 프론트는 메모를 화면에서 제거하고 복원 안내를 보여준다.

### 보류 처리 중 연결선이 바뀐 경우

보류 상태 변경과 해당 연결선 영구 삭제를 하나의 트랜잭션으로 처리한다. 연결선 버전이 충돌하면 보류 전체를 취소하고 최신 연결 상태를 보여준다. 성공하면 연결선 행은 복구할 수 없고 감사 로그만 남는다.

### 보류 메모를 복원한 경우

`held_from_section_id`가 현재 PRD의 활성 섹션이면 그 섹션으로 복원한다. 섹션이 없거나 삭제됐으면
미분류 영역의 안전한 기본 좌표로 복원한다. 과거 연결선은 자동 복원하지 않는다.

### 중복 또는 자기 연결

서버가 `409 Conflict` 또는 검증 오류를 반환한다. 프론트에서 막았더라도 서버 검증을 생략하지 않는다.

### 필터가 연결된 상대 노드를 숨긴 경우

연결선만 떠 있는 상태를 만들지 않는다. 양쪽 노드가 모두 보일 때만 연결선을 렌더링한다. 데이터는 유지한다.

### 자동 정렬 중 다른 사용자가 노드를 옮긴 경우

일괄 요청에 노드별 버전을 포함한다. 하나라도 충돌하면 부분 적용하지 않고 전체 transaction을
취소하며 최신 충돌 노드를 반환한다.

### AI 분석 대상이 없는 경우

빈 캔버스에서는 AI를 호출하지 않는다. `분석할 메모가 없습니다`를 반환해 비용을 사용하지 않는다.

### AI 분류 결과가 유효하지 않은 경우

존재하지 않는 섹션 추천, 중복 노드, 누락 노드는 제외하고 오류 내역을 기록한다. 유효한 추천도 사용자 확인 전에는 저장하지 않는다.

### AI 요청이 느리거나 실패한 경우

타임아웃 후 로딩 상태를 종료하고 재시도 버튼을 제공한다. 재시도는 같은 작업 ID를 사용할 수 있지만 새 데이터가 생겼다면 최신 버전으로 다시 분석한다.

### AI 요청 중 사용자가 취소한 경우

화면만 닫지 않고 서버 작업을 취소한다. 취소된 결과가 늦게 도착해도 화면이나 PRD에 반영하지 않는다.

### 미리보기 후 메모가 변경된 경우

이전 미리보기로 PRD에 반영하지 않는다. `409 Conflict`를 반환하고 변경된 메모를 표시한 뒤 미리보기를 다시 생성한다.

### PRD 반영 요청이 중복된 경우

idempotency key와 반영 기록을 확인해 같은 답변을 두 번 추가하지 않는다.

### 일부 섹션만 반영에 실패한 경우

하나의 반영 요청에서 사용자가 승인한 질문들은 단일 transaction으로 처리해 전체 성공 또는 전체
실패를 보장한다. 질문별 선택은 요청 전에 사용자가 결정하며 저장 중 부분 성공은 허용하지 않는다.

### 인터넷 연결이 끊긴 경우

저장되지 않은 편집을 화면에 표시하고 무조건 성공한 것처럼 보여주지 않는다. 재연결 후 최신 데이터를 다시 받은 뒤 충돌 여부를 확인한다.

### 참여자가 탈퇴하거나 비활성화된 경우

이름과 과거 작성 기록은 유지한다. 새 담당자 지정 대상에서는 제외한다. 해당 사용자가 담당자였던 메모는 작성자를 담당자로 되돌린다.

### 작성자도 탈퇴한 경우

작성자 기록과 담당자 값은 유지할 수 있지만 해당 사용자는 편집할 수 없다. 관리자가 활성 참여자에게 담당자를 재배정한다.

### 튜터 코멘트가 최종 PRD에 크게 반영된 경우

튜터의 코멘트는 반영 여부와 관계없이 기여도 계산에서 제외한다. 최종 PRD에 영향을 준 사실은 감사 기록이나 별도 참고 정보로만 남긴다.

### owner의 일반 코멘트가 반영된 경우

owner가 팀원으로 작성한 일반 코멘트는 다른 팀원의 코멘트와 같은 기준으로 AI가 반영 정도를 평가한다. owner 역할이라는 이유로 제외하지 않는다.

### AI 기여도 평가가 실패한 경우

PRD 완료는 유지한다. 기여도 결과를 임의의 0점으로 확정하지 않고 실패 상태로 저장해 관리자 재시도를 허용한다.

### 기여도 평가 결과의 신뢰도가 낮은 경우

낮은 신뢰도 결과를 표시하고 관리자 검토 대상으로 보낸다. 관리자가 수동으로 점수를 바꿀 수 있게 한다면 원본 AI 결과와 수정 사유를 모두 보존한다.

### 삭제 후 30일이 지난 경우

영구 삭제된 데이터는 복원할 수 없다. 복원 요청에는 `410 Gone` 또는 명확한 만료 오류를 반환한다.

## 29. 초기 목업 대비 확정된 처리

초기 목업에서 발견된 저장·권한 공백은 다음 정책으로 정리했다.

- 작성자와 최초 담당자는 로그인 사용자로 지정한다.
- 보류 시 메모는 유지하고 섹션을 해제하며 연결선은 감사 기록을 남긴 뒤 영구 삭제한다.
- 사용자 삭제는 30일 소프트 삭제로 처리한다.
- 분류 결과의 정확한 개수는 서버가 계산하며 AI 분석·항목 분류 UI는 제거한다.
- AI PRD 반영은 미리보기 ID, 노드·질문 version과 사용자 승인을 거쳐 저장한다.
- 모든 방향의 섹션 이동을 허용하고 `section_id`를 서버에서 검증한다.
- 연결선은 DB UUID, FK·유니크 제약과 idempotency key를 사용한다.
- viewport는 사용자·캔버스별로 저장한다.
- 기여도 결과는 staff/superuser 관리자에게만 공개한다.
- 브레인스토밍 Markdown 내보내기는 제거했다.
- HTTP polling과 cursor 재동기화를 제공하며 실시간 커서·프레즌스는 제공하지 않는다.

제목 카드 생성 UI와 실행 취소·다시 실행 UI는 별도 제품 결정 전까지 확장하지 않는다.

## 30. 인수 조건

- PRD 유형에 맞는 실제 섹션이 칸으로 반환된다.
- 새 메모는 미분류로 생성되고 로그인 사용자가 작성자와 최초 담당자가 된다.
- 메모를 모든 방향으로 섹션 간 이동할 수 있다.
- 이동은 마우스를 놓을 때 최종 좌표와 섹션을 한 번 저장한다.
- 보류하면 메모는 남지만 섹션과 연결선은 해제된다.
- 보류 메모를 해제하면 유효한 직전 섹션으로 돌아가고, 그렇지 않으면 미분류 기본 위치로 돌아간다.
  과거 연결선은 자동 복원되지 않는다.
- 삭제한 노드는 30일 안에 복원할 수 있다.
- 자기 연결과 중복 연결은 서버에서 차단된다.
- 필터로 노드가 숨겨져도 노드와 연결선 데이터는 삭제되지 않는다.
- 자동 정렬은 한 번의 일괄 저장과 하나의 변경 기록으로 처리된다.
- 화면의 분류 결과와 모든 정확한 개수는 AI가 아니라 서버가 계산한다.
- Legacy AI 분류와 현재 AI PRD 적용은 사용자 확인 전 원본을 변경하지 않는다.
- AI PRD 적용 결과에는 질문별 초안과 근거 노드 ID가 포함된다.
- AI는 기존 답변과 선택된 메모를 통합하고 사용자가 승인한 질문만 저장한다.
- 미리보기 후 데이터가 바뀌면 이전 결과로 PRD에 반영되지 않는다.
- 같은 반영 요청이 재전송돼도 PRD 내용이 중복 생성되지 않는다.
- 화면 위치와 확대 비율은 사용자별로 복원된다.
- 동시 수정 충돌은 `409 Conflict`와 최신 데이터로 처리된다.
- 재연결 시 노드·연결선·통계를 서버에서 다시 동기화한다.
- 새 메모의 담당자를 다른 참여자로 변경할 수 있다. 기여도는 담당자 변경이 아니라 lineage의
  작성자·내용 편집자와 실제 PRD 반영 confidence를 사용한다.
- 튜터는 코멘트할 수 있지만 코멘트 기여도 계산에서는 제외된다.
- owner의 일반 코멘트는 팀원 기여도 계산에 포함된다.
- 완료 후에도 튜터는 기여도에서 제외되는 리뷰 코멘트를 작성할 수 있다.
- AI는 일반 참여자의 코멘트가 최종 PRD에 반영된 정도와 근거를 반환한다.
- 완료 후에는 관리자 또는 소유자가 재개하기 전까지 편집할 수 없다.

## 31. 꼭 지킬 원칙

- 모든 API에서 로그인과 PRD 권한을 확인한다.
- PRD 캔버스 버전은 `(prd_id, version_number)`로 유일하며 최초 진입은 최신 버전을 연다.
- 버전 목록의 첫 보드만 최신·편집 가능하며, 순서를 바꾸면 최신 지정도 함께 바뀐다. 이전 보드는 조회 전용이고 최신 삭제 시 다음 보드를 자동 승격한다.
- 버전 복제로 생긴 동일 메모는 `lineage_id`로 식별해 기여도에서 중복 집계하지 않는다.
- 작성자와 최초 담당자는 로그인 사용자로 지정하고 작성자는 이후 바꾸지 않는다.
- 담당자는 변경할 수 있지만 담당자 변경 자체는 기여가 아니다. 기여도는 lineage의 작성자·의미
  있는 내용 편집자와 실제 PRD 반영 confidence를 기준으로 한다.
- 참여 중인 담당자가 제거되면 담당자는 해당 메모 작성자로 돌아간다.
- 보류 메모 자체는 삭제하지 않지만 섹션은 해제하고 연결선은 영구 삭제한다.
- 보류 해제 메모는 유효한 직전 섹션으로 돌아가고, 섹션이 없으면 미분류로 돌아간다. 과거 연결선은 자동 복구하지 않는다.
- 삭제는 소프트 삭제하며 30일 동안 복원할 수 있다.
- 섹션 분류는 `section_id`로 저장하고 좌표로 추측하지 않는다.
- AI 결과는 사용자 확인 전 원본 데이터와 PRD를 바꾸지 않는다.
- PRD 반영은 일회성 저장이며 자동 양방향 동기화하지 않는다.
- AI 통계와 정확한 개수는 서버가 계산한다.
- AI PRD 적용은 섹션, 질문, 메모를 구조화해 전달하고 질문별 근거를 저장한다.
- AI는 기존 답변과 메모를 통합하며 승인 전에는 기존 답변을 변경하지 않는다.
- 튜터·관리자 지도 코멘트는 기여도에서 제외한다.
- 일반 참여자의 코멘트 반영 정도는 AI가 근거와 함께 평가한다.
- 완료된 PRD는 관리자가 재개하기 전까지 잠근다.
- 완료 후 튜터 리뷰 코멘트는 허용하되 기여도와 PRD 내용에는 직접 반영하지 않는다.
- 동시 수정은 버전으로 충돌을 감지한다.
- 중복 생성과 중복 반영은 idempotency key로 막는다.
- 현재 UI에 없는 미결정 기능을 백엔드 확정 기능으로 먼저 구현하지 않는다.

## 32. 확정된 추가 정책과 남은 결정 사항

### 확정: PRD 답변 병합 방식

AI가 기존 답변과 선택된 메모를 하나의 답변으로 통합한다. 변경 전·후와 근거를 보여주고 질문별 사용자 승인 후 저장한다.

### 확정: 기여도 최종 가중치

다음 값으로 고정한다.

```text
코멘트 기여도 50% + 채택 메모 기여도 50%
```

### 확정: owner와 튜터 코멘트

- owner의 일반 코멘트: 기여도 포함
- 튜터의 지도·리뷰 코멘트: 기여도 제외
- 완료 후 튜터 리뷰 코멘트: 허용하되 PRD 수정은 불가

### AI 기여도 결과 이의 제기와 관리자 수정

AI가 잘못 평가했다고 판단할 때 다음 중 어느 수준까지 허용할지 정해야 한다.

- 재평가만 허용
- 관리자가 점수를 수정
- 관리자가 코멘트별 반영 여부만 수정하고 점수는 다시 계산

관리자가 AI 기여도 점수를 직접 수정하거나 이의 제기를 처리하는 기능은 현재 보류한다. MVP에서는 AI 원본 결과와 근거를 저장하고, 필요하면 동일 입력으로 재평가만 수행한다.

### 확정: 보류 시 연결선

보류 시 연결선은 영구 삭제한다. 복원 시 연결선을 자동 복구하지 않고 감사 로그에 삭제 사실과 두 노드 ID만 남긴다.

### AI 실행 모델과 운영 설정

기능 정책과 별개로 실제 구현 시 모델, 타임아웃, 재시도, 사용량 제한, 비동기 작업 방식을 설정해야 한다. 이 값들은 코드에 흩어놓지 않고 기능별 설정이나 프롬프트 버전으로 관리한다.

## 33. 부모 시스템과 회차 연동

브레인스토밍은 해당 PRD의 참여 관계를 기본 접근 경계로 사용한다. PRD가 회차에 연결되어 있으면
부모 AX2 시스템의 해당 회차·팀 맥락을 추가 검증하고, 회차 없는 PRD이면 명시적인 참여 역할과
활성 사용자 검증으로 동작한다.

기술 스택은 부모 시스템과 동일하게 사용한다.

- Django
- Bootstrap
- PostgreSQL

React/Tailwind 원본은 Figma 목업 참고자료로만 보관한다. 현재 브레인스토밍 화면은 부모 호환
Django template과 Bootstrap 레이아웃 안에서 React를 CDN 방식으로 사용한다.

```text
부모 base template
└── Bootstrap 화면과 공통 내비게이션
    └── #brainstorm-root
        └── React CDN 브레인스토밍 앱
```

React는 캔버스 드래그, 확대·축소, 연결선, 화면 상태 갱신을 담당한다. Django는 인증, 회차 Context, 초기 화면 렌더링, API, CSRF, 동기화 권한을 담당한다.

독립 시스템에 부모와 호환되는 `templates/base.html`을 만들고 `extra_head`, `breadcrumb`, `content`, `modals`, `extra_js` block을 제공한다. `extra_head`에는 브레인스토밍 전용 CSS와 고정 버전 React CDN을, `content`에는 `#brainstorm-root`를, `extra_js`에는 JSX 없는 브레인스토밍 정적 JavaScript를 배치한다. `CSRF_COOKIE_HTTPONLY = true`를 사용할 경우 API 요청의 CSRF 값은 쿠키를 읽지 말고 Django 템플릿이 DOM에 렌더링한 토큰에서 가져온다.

부모 저장소에는 현재 Redis, Celery, Django Channels, WebSocket 라우팅이 없다. 스택 호환성을 위해 단독 시스템 MVP도 HTTP polling을 사용한다. 변경 이벤트에 증가하는 ID 또는 `updated_at` cursor를 두고 2~5초 간격으로 증분 조회하며, 재연결 시 전체 상태를 다시 조회한다. 저장 충돌은 기존 시나리오의 `version`과 `409 Conflict`로 막는다.

HTTP polling 단계에서는 다른 사용자의 저장 완료 후 변경 반영은 지원하지만, 부드러운 실시간 마우스 커서와 순간적인 프레즌스는 제공하지 않는다. 부모 이식 팀이 이 두 기능을 필수로 정하면 Django Channels와 Redis Channel Layer를 신규 도입해야 한다는 이관 메모를 남긴다.

Tailwind 런타임은 사용하지 않고 Bootstrap과 브레인스토밍 전용 CSS를 사용한다. React와 ReactDOM CDN 버전은 고정하고 부모 CSP에 허용 도메인을 등록한다. JSX를 브라우저에서 즉시 변환하는 개발용 Babel CDN은 운영에서 사용하지 않는다. 운영 JavaScript는 JSX 없는 정적 파일 또는 사전에 변환된 파일로 제공한다.

React CDN 로딩 실패 시 캔버스 대신 재시도 안내를 표시하고, 다른 Django·Bootstrap 화면은 정상 동작해야 한다.

사용자·회차·팀 정보는 부모 시스템의 읽기 전용 VIEW에서 조회한다.

- `public.ax_user_team_login_view`
- `public.user_round_team_view`

회차별 팀 소속은 `user_id + round_id`로 판단한다. 사용자의 최신 대표 팀을 현재 팀으로 간주하지 않는다.

브레인스토밍 요청은 다음 맥락을 가진다.

```text
user_id
round_id 또는 null
participant_id 또는 null
team_id 또는 null
prd_id
role
```

회차 PRD는 PRD의 `round_id`를 기준으로 사용자의 `user_id + round_id` 참가정보를 다시 확인한다.
팀 전용 PRD라면 PRD의 `team_id`와 해당 회차의 팀 소속도 확인한다. 현재 선택 회차와 다르다는
이유만으로 명시적 참여자가 과거 PRD를 조회하지 못하게 하지 않는다.

사용자를 메모 담당자로 지정할 때 대상 사용자가 해당 PRD의 활성 참여자인지 검사한다. 회차 PRD는
대상 사용자의 해당 회차 참가정보도 확인하고, 회차 없는 PRD는 활성·승인 사용자 VIEW와 명시적
PRD 참여 관계를 확인한다.

부모 VIEW는 조회 전용이다. 브레인스토밍 메모, 코멘트, 담당자, 기여도 결과는 자식 시스템이 소유한 테이블에 저장하고 부모 VIEW에는 쓰지 않는다.

우리 팀은 단독 시스템만 구현한다. 부모 팀이 이식할 때 서비스·권한 코드를 다시 쓰지 않아도 되도록 로그인 사용자와 현재 회차를 해석하는 부분만 연동 어댑터로 분리한다.

```text
IntegrationContextResolver
- standalone: 자체 Django 세션 사용자와 외부 user_id 매핑, 부모 VIEW 조회
- test: 부모 VIEW와 같은 형식의 fixture 사용
- handoff contract: 부모 팀이 필요하면 부모 request.user resolver로 교체
```

단독 시스템의 로그인 신원과 세션은 자체 Django `request.user`를 사용한다. VIEW는 인증을 대신하지 않으며, 로컬 사용자와 VIEW의 `user_id`를 명시적으로 매핑한다. 부모 팀이 이식할 때는 부모 `request.user.pk`와 VIEW의 `user_id`를 대조하도록 resolver를 교체할 수 있어야 한다.

현재 회차는 회차 기반 신규 작업의 기본 문맥으로만 사용한다. VIEW에서 진행 중 회차가 하나면 기본
선택하고 여러 개면 사용자가 선택한 값을 검증하며, 임의의 최신 회차를 고르지 않는다. 진행 중
회차가 없어도 회차 없는 PRD와 명시적으로 참여 중인 과거 PRD의 브레인스토밍은 사용할 수 있다.

VIEW 조회가 실패해 사용자 활성 상태나 회차 참가정보를 검증할 수 없으면 검증이 필요한 메모
생성·수정·AI 반영 같은 쓰기 요청을 허용하지 않는다.

PRD 완료 시 회차 PRD의 기여도 계산 대상은 그 PRD와 같은 `round_id`의 유효한 참여자로 제한한다.
회차 없는 PRD는 완료 시점의 활성 PRD 참여자를 대상으로 한다. 어느 경우에도 다른 회차의 팀
소속이나 다른 PRD의 코멘트를 섞지 않는다.
